# Blender pipeline

Every model in Chain Reaction City is generated by Python in `tools/blender/`.
There are no hand-modelled files. Delete `assets/models/` and re-run the three
build scripts and the same 172 models come back.

**Blender 5.2 LTS**, driven over MCP. Python 3.13.

---

## Why code, not hand modelling

Three reasons, in order of how much they mattered:

1. **The art direction is systematic.** Chunky low-poly toys with a consistent
   bevel and a fixed palette are a set of rules, and rules are better expressed
   as code than repeated by hand across 172 objects.
2. **Physics needs exact numbers.** The level builder reads real exported
   dimensions out of `art/exports/*.json` to place things at the correct rest
   height. If a model changes, every level that uses it re-derives.
3. **It stays honest.** A regenerated library can be diffed. A hand-edited one
   drifts from its documentation immediately.

## Layout

```
tools/blender/
  toykit.py         shared toolkit: palette, primitives, bevel, export
  build_hero.py     39 models — cannon, ball, dominoes, car, blocks, celebration
  build_world1.py   50 models — triggers, ramps, targets, street dressing
  build_kits.py     83 models — movers, mechanical, air, water, electrical,
                    destructible, world 2-5 dressing
  render_check.py   rebuilds logo.png's composition and renders it, to validate
                    proportions and palette before anything reaches the game
art/blender/        saved .blend per kit
art/exports/        per-kit JSON manifest (tris, materials, size, purpose)
```

Running a kit from Blender:

```python
import sys
sys.path.insert(0, r"<repo>/tools/blender")
import build_hero
build_hero.run()
```

## Conventions

These are enforced by `toykit.py` rather than by discipline.

| Rule | Why |
| --- | --- |
| Units are metres; toys are 0.05–1.2 m | Real gravity then produces toy-scale timings |
| Build Z-up in Blender, think Y-up in Dart | glTF export converts; the runtime is Y-up |
| Anything with a front faces **+X** | Levels run left to right, so +X is "forward" everywhere |
| Pivot at the bounding-box centre | Mesh and physics body then share an origin, so there is no per-asset offset table |
| Transforms applied before export | Nothing carries a hidden scale into the runtime |
| Flat shading everywhere | The renderer shades per face from geometry |

### Colour

`toykit.PALETTE` holds the values sampled from `logo.png` and is the twin of
`lib/engine/render/palette.dart`. Blender node colours are **linear**, so hex
values are converted on the way in (`hex_to_linear`) and the glTF
`baseColorFactor` is converted back to display space by the runtime loader.
Getting this wrong is the classic washed-out-colours bug.

The validation render initially came out pastel because Blender 4+/5 defaults
to the **AgX** view transform, which deliberately desaturates. `render_check.py`
sets `view_transform = "Standard"`.

### Bevels

Every model gets an angle-limited bevel. It is what makes a plain box read as
moulded plastic instead of a primitive, and it is the single biggest
contributor to the look.

One exception, and it is instructive: **balls are not bevelled.** An
angle-limited bevel on an icosphere cuts every facet edge and shrinks the
silhouette by roughly 10%, which put the visual radius out of step with the
sphere collider. The icosphere's own facets already give the faceting the
reference has, so the true radius is preserved instead.

Blender's `subdivisions=1` is the bare 20-face icosahedron, which reads as a
gem rather than a ball. Balls use `subdivisions=2` — 80 faces, still obviously
faceted at mobile size.

## Export settings

Set once in `toykit.export()`:

```python
bpy.ops.export_scene.gltf(
    export_format="GLB", use_selection=True, export_apply=True,
    export_yup=True, export_materials="EXPORT",
    export_normals=False, export_texcoords=False, export_tangents=False,
    export_skins=False, export_morph=False, export_animations=False,
    export_cameras=False, export_lights=False, export_extras=False,
    export_attributes=False, export_shared_accessors=True,
)
```

Normals are **off on purpose**. The renderer derives a face normal from the
geometry at load time, so normals in the file would be bytes that are read and
thrown away.

## Multi-part assets

Parts that need to move independently are exported as separate models and
composed at runtime:

- `cannon_barrel` / `cannon_carriage` / `cannon_wheel` — the barrel recoils
- `toy_car_body` / `toy_car_wheel` — the wheels roll
- `flag_base` / `flag_cloth` — the cloth rises up the pole
- `chest_base` / `chest_lid` — the lid hinges

Everything else is joined into one object, because the GLB loader merges all
primitives into a single mesh anyway: a twelve-object Blender assembly still
costs one instance and one bounding box at runtime.

## Validation

`render_check.py` re-imports the **exported GLBs** — not the in-memory
meshes — and rebuilds the exact composition from `logo.png` in a white studio
with soft key/fill lighting and a long lens. Output goes to
`art/exports/hero_check.png`.

Re-importing rather than rendering the source scene is deliberate: it validates
the shipped files, which is where orientation, scale and material errors
actually surface.
